# Changelog

Each release section below has four parts, in this order: **What's new** (the gist), **Breaking changes** (what an existing app must act on), **Upgrading** (where the steps are) and **Full list of changes** (every entry, with the App migration steps written for agents).

Each entry lists convention changes and what an existing app must do about them. `/offrails:upgrade` reads this file, so write the **App migration** notes as instructions for an agent.

## 0.7.2 (2026-10-18)

### What's new

- **`cargo offrails verify`** runs the Definition of Done in parallel in one command. `--fast` (after every change) runs fmt, clippy and the SQLite and Postgres suites at the same time; `--full` (once, at the end) adds coverage, `cargo deny`, gitleaks and the other checks. A bare app's loop after a one-line change went from 140 s to about 6 s.
- **Generators:** `cargo offrails generate <kind>` (`g`) writes migrations, models, CRUD resources, controllers, pages, APIs, jobs, mailers, channels and tests that follow the guides and come with their tests. `cargo offrails destroy` (`d`) removes exactly what was generated and is still unchanged.
- **`cargo offrails update-part`** brings a newer version of an installed part into the app with a three-way merge: clean changes apply, overlapping edits get conflict markers, and the app's own changes are never silently overwritten.
- **Faster Postgres tests:** the suite migrates once into a template database and reuses locked slot databases reset before each test, instead of creating and migrating a database per test.
- **A browser smoke for boosted navigation** catches page JavaScript that works on a fresh load but is dead after a boosted link. Page scripts now load from the layout and bind by delegation.
- **Template speed-ups:** one CI test job instead of two, a cached Docker dependency layer, and a cached development CSS check.

### Breaking changes

Nothing is required to keep an existing app working. Before using the new tools:

- Generators need the `// samples:` anchors in the shared files; a generator that lacks one refuses and names it.
- The route-sweep tests (`smoke_test.rs`, `security_test.rs`) must send each route's own method before the first `cargo offrails g api`.
- Parts updated to this release load their page scripts at a new `samples: app head` anchor in the layout.
- `split-debuginfo` left `[profile.dev]` in the template; an app built on Windows must remove it too.

### Upgrading

Follow the ordered list below; each step's Detect/Converge/Prove is in the entry it names under Full list of changes, and [upgrade](generators/upgrade.md) is the whole procedure. `$FW` is the new framework.

1. **Parts first, before re-vendoring:** `update-part` merges against the part as installed in `.offrails/`, so run it while `.offrails/` is still the old release: `cargo offrails update-part <each installed part> --framework "$FW" --dry-run`, then without `--dry-run`. Resolve any `<<<<<<<` markers, then `cargo fmt --all` and `cargo run -q -- db migrate`. (An app on 0.7.1 or older has no `update-part` yet: run the new release's, `cargo run -q --manifest-path "$FW/tools/offrails-gen/Cargo.toml" -- update-part <part>… --framework "$FW" --app .`.)
2. **Re-vendor:** `offrails-gen vendor --framework "$FW"`. `cargo offrails verify`, `generate`, `destroy` and `update-part` now work.
3. **Generator anchors** (Generators → App migration): add every missing `// samples:` anchor. A generator that needs a missing one refuses and names it, so this can wait until the first `generate`.
4. **Route sweeps send each route's own method** (same entry): required before the first `cargo offrails g api`.
5. **Optional speed-ups** (Fast loop → App migration): Postgres test slots, the CSS check cache, the `split-debuginfo` move (needed for Windows builds), and the one-job CI.
6. **Prove it:** `cargo offrails verify --full` is green on SQLite and Postgres, `sh .offrails/tools/offrails-check` reports 0 errors, and `docs/decisions.md` has `YYYY-MM-DD: upgraded to framework 0.7.2` plus the generators line.

### Full list of changes

- **A fast loop: `cargo offrails verify`** ([workflow](workflow.md#definition-of-done)). A human, after a 41-minute agent build and 4+ minute CI runs: "we need CI to run in 10 seconds or less, can't we parallelize or something". The Definition of Done ran sequentially (fmt, clippy, SQLite suite, Postgres suite, coverage, deny, gitleaks, browser smokes), and the docs had agents run all of it after every change. Now one cross-platform command (in `offrails-gen`, so `cargo offrails verify` works in every template app) runs it in parallel:
  - `--fast` (default; after every slice): `cargo fmt --check`, the CSS build (htmx), clippy `-D warnings` in its own target dir (`target/clippy`, so it compiles while the tests build), the test binaries once, then the SQLite and Postgres suites **at the same time** (nextest; Postgres runs the integration tests, since unit tests never read `TEST_DATABASE_URL`). One line per step with its time and test counts, the tail of each failure, logs in `target/verify/`, non-zero exit on any failure. Postgres comes from `TEST_DATABASE_URL` (environment or `.env`) or the compose URL when `localhost:${DB_PORT:-5432}` answers; otherwise it says **skipped**.
  - `--full` (once, at the end): also `offrails-check`, coverage (it *is* the SQLite run, instrumented with `cargo llvm-cov nextest --fail-under-lines 80`), `cargo deny`, gitleaks, the no-`unwrap`/`expect` review, `routes` vs `docs/routes.md`, the TS checks when there is a `web/`, and the browser smoke when `BASE` names the running app. Missing tools are reported as `skip` with the install command, never as passed.
  - The guidance changed with it: [workflow](workflow.md) (the loop's VERIFY step, the Definition of Done, "iterate fast, verify fully once": one test with `cargo nextest run <name>` while red, `verify` after each slice, coverage/deny/gitleaks/full browser smokes only in `--full`), CHEATSHEET, `/offrails:check`, the app `AGENTS.md` blueprint, [new](generators/new.md) step 5, `offrails-gen new`'s next steps, `tools/ci/test-template.sh` (now runs `verify`, still failing on any flaky test outside its known list).
  - Measured on generated apps (Apple M2, 8 cores, macOS; other agents were compiling on the same machine the whole time, so each row gives the load average, and old and new were run back to back under the same load). "Old" is 0.7.1's template and its sequential Definition of Done; "new" is this release.

    Where an all-parts app's 34 s go: the test build (~12 s, the app crate compiled as lib and as lib-test in parallel, then the test binary), then the Postgres suite (~20 s beside SQLite, ~14 s alone; 461 integration tests, the longest single tests 4–5 s of real timeouts in the parts' own tests). The 10 s target holds for the bare app, not for one with every part.
- **Postgres tests: no `CREATE DATABASE` and no migrations per test** ([testing](guides/testing.md#postgres-test-databases)). Each test used to create `test_<crate>_<uuid>`, migrate it and drop it. `CREATE DATABASE` copies and fsyncs a template (measured on this machine under load: 1.2–3.8 s for one empty database), so the Postgres run degraded badly when the machine was busy (a 541-test blog: 42.5 s quiet, 335 s at load ~68). Now `support.rs` migrates once into `test_<crate>_<tag>_tpl` (`<tag>`: a hash of the migration names and files, so an edited migration builds a new one; built under an advisory lock and renamed into place, so concurrent first tests wait and a killed build leaves nothing half-migrated), each concurrent test locks a slot `test_<crate>_<tag>_<n>` (`pg_try_advisory_lock`), cloned from the template once and reused across tests and runs, with `synchronous_commit = off`, and `offrails_test.reset()` puts the slot back to the just-migrated state before every test: tables with rows truncated, the migrations' seed rows and every sequence restored. A schema fingerprint makes the reset refuse a slot a test changed (rolled a migration back, created a table), and the harness re-clones it. Still every test on both databases, isolated. Also evaluated: a rollback transaction per test (rejected: the app's own transactions, the job worker and realtime use other connections) and `CREATE DATABASE … TEMPLATE` per test (keeps the fsync cost). SQLite stays in-memory and migrated per test: the migrations are ~5 ms of a ~40 ms median test. The new SQL is in `kernel::db` (`database_exists`, `create_database_from`, `rename_database`, `advisory_lock`/`try_advisory_lock`/`advisory_unlock`, `skip_commit_flush`, `install_test_reset`/`reset_test_database`, `drop_idle_stale_test_databases`), with a kernel test (`the_postgres_test_reset_empties_tables_and_refuses_a_changed_schema`).
- **The development CSS check is cached** ([views](guides/views.md#dark-mode)). `kernel::css::css_warning` read every template and the built CSS on every development page (~85 ms in a grown app; 97% of the CPU under load). It now recomputes only when a template, `assets/app.css` or `static/app.css` changes (size and mtime), with a unit test.
- **Template CI: one test job** ([testing](guides/testing.md#ci)). The `sqlite` and `postgres` jobs each compiled the tests; the new `test` job runs `cargo offrails verify --fast` against a Postgres service on tmpfs, with rust-cache keeping `target` and `target/clippy`, after the migration guard, `offrails-check` and a `cargo metadata --locked` check. The Docker job's `Dockerfile` builds the dependencies in a layer of their own (a placeholder `src/`), which the `gha` layer cache keeps; the old `--mount=type=cache` target was never in that cache, so every run compiled every dependency in release mode. Locally (Docker on the M2, bare app, load 18→77): the first image build 352 s, a rebuild after a one-line code change 156 s with the dependency layer reused (the app crate's release compile and the CSS), and the image boots (`/up` 200). Not measured on GitHub (no runner available to this change): expected, from the local split, that a code-only push skips the release dependency build (most of the Docker job) and compiles the tests once instead of twice.
- **A dev-dashboard test failed for good after ~50 runs in one working copy** (`run_history_is_capped_redacted_and_reopened`). It saved a run dated 2027 into the real `storage/dashboard/ai-runs/` and never removed it; once `MAX_HISTORY` of them piled up they outranked and pruned the run the test makes. It now deletes its file. A local change to `template/parts/dev-dashboard` (the samples repo needs the same one-line fix; `tools/sync-parts.sh` would undo it). Its other flake (another test process pruning the shared history) remains in `test-template.sh`'s known list.
- **Build settings** ([testing](guides/testing.md#build-speed)). `split-debuginfo = "unpacked"` left `[profile.dev]`: Windows MSVC refuses it, and it is macOS's default anyway; Linux gets it from `.cargo/config.toml` (`[target.'cfg(target_os = "linux")']`). Faster linkers stay opt-in per machine (`~/.cargo/config.toml`; x86_64 Linux already uses rust-lld since Rust 1.90). sccache is documented as an optional shared cache for a second app on one machine; a shared `CARGO_TARGET_DIR` is not recommended (one build lock for every app and agent).

- **Generators you run, not recipes you copy: `cargo offrails generate <kind> …` (`g`) and `cargo offrails destroy <kind> <name>` (`d`)** ([generators](generators/README.md)). The human: "can we add actual code generators similar to rails? so the agent can invoke those instead of just copying? like db migrations, new controller, new api route, new page, and especially the parts… i hope this would make things even faster." Field types: `string text integer bigint boolean decimal{p.s} money datetime date uuid json references{model}` with `?`/`:optional`, `:unique`, `:index`, each mapped to its column, Rust type, form control, validation and factory value. Generated code follows the guides exactly: 64-bit ids and FKs (`offrails-check [ids]`), per-user scoping when the app has accounts (`find_for`, raw `find` model-private, another user's id is 404, unique-per-owner indexes, references checked against the actor), `Access` rows, `paths::` helpers, docs/routes.md, `#[instrument(skip_all)]` on every action and model fn, no `unwrap`/`expect` outside tests, templates in the design tokens with every `dark:` partner, and request tests for happy paths, 422s, sign-in, tenancy (`guard_test.rs` + an anchored `tenancy_test.rs`), escaping and the N+1 guard, on SQLite and Postgres. - **A browser smoke for boosted navigation: every page must work after a boosted link, not only on a fresh load** ([frontend-htmx](guides/frontend-htmx.md#boosted-navigation), [testing](guides/testing.md#browser-smoke-boosted-navigation)). The sign-in page's password **Show** button worked on a direct load and was dead after clicking through to the page: `auth.js` loaded in the page's `{% block head %}`. Request tests and screenshots can't see it.
  - **`.offrails/tools/browser-smoke/smoke-boosted.mjs`**: for each GET route in `docs/routes.md` without a parameter that is a boosted HTML page (kernel pages, JSON and streams are skipped and listed; a route that redirects smokes the page it lands on), it clicks the page's live elements after a full load and records which react (DOM or attribute change, print, copy, dialog), then loads `/`, follows a boosted link to the page and clicks them again. It fails on an element that is dead after the boosted link, on a script or stylesheet the page loads in its own `<head>`, and on any console error, uncaught exception or CSP violation on either path. With password sign-in it runs signed out, then signed in as the demo account. Zero dependencies: Node ≥ 18 and the installed Chrome, Chromium or Edge (`CHROME_PATH`, else the usual places on macOS, Linux and Windows), driven over the DevTools Protocol on a pipe; it never downloads a browser. Without one it prints `skip: no Chrome` and exits 77.

## 0.7.0 (2026-10-16)

### What's new

- **Security fix: development is reachable only from this machine.** `serve` binds `127.0.0.1` in development (`APP_BIND`) and answers only local and configured host names (`APP_ALLOWED_HOSTS`), so another device on the network or a DNS-rebinding page can no longer open `/dev` (where the mailbox shows sign-in links). A new `offrails-check [bind]` rule enforces it.

- **Less leakage:** job errors are stored redacted, `Config`'s `Debug` prints only settings that can never hold a secret, and presence labels never come from an email address.
- **Samples:** optional, tested reference code for the mailer, jobs, sign-in, realtime and a dev dashboard in [rust-off-rails/samples](https://github.com/rust-off-rails/samples). Upgrading offers them per area.

- **Every app:** the development server must bind `APP_BIND` (default `127.0.0.1` in development) and check `Host`; `offrails-check` fails with `[bind]` until it does. A dev container, tunnel or LAN workflow now needs `APP_BIND=0.0.0.0` plus `APP_ALLOWED_HOSTS`.
- **Apps with accounts:** sign-in destroys the old session; reset and login links get per-address and daily limits; apps with signup (or both passwords and login links) add a nullable `email_verified_at` column, and a user's first reset after the upgrade also revokes their API tokens.
- **Apps with a manual theme toggle:** the cookie is renamed from `theme` to `offrails_theme` (read the old one for one release).

## 0.6.2 (2026-10-13)

### What's new

- **`offrails-check` catches 32-bit ids** (`[ids]`), which pass on SQLite and break every Postgres write, and test suites that never run on Postgres (`[postgres]`).
- **`bin/dev` manages its own process:** it writes a PID file per server, refuses to start twice on one port, and on exit stops only its own process tree. Agents stop a server with `kill "$(cat storage/pids/…)"`.
- **Seeds can be re-run** after a half-failed run: one transaction, each record found or created by a natural key.
- **WebSockets sized for many sockets:** smaller per-socket buffers took 10,000 sockets from 1.37 GB to 160–225 MB.
- **Whole files in the guides** for `kernel/tls.rs` and `kernel/introspect.rs`, and a pattern for live boards over a channel (snapshot, patches, reducer).
- **Parallel helpers only after the skeleton compiles,** each with its own files.

### Breaking changes

- `offrails-check` fails on the new `[ids]` and `[postgres]` rules: an app with 32-bit ids adds a widening migration (never edits the applied ones), and `tests/app/support.rs` must read `TEST_DATABASE_URL`.
- `bin/dev` no longer uses `trap 'kill 0'` (it could kill the caller's shell); copy the new top of the script.

## 0.6.1 (2026-10-13)

### What's new

- **Sign-in over dev HTTPS works again:** development serves HTTPS only with a locally trusted (mkcert) certificate, and otherwise plain HTTP with a message saying why. `APP_DEV_HTTP_PORT` serves plain HTTP beside TLS.
- **Dark mode that stays readable:** a palette, layout skeletons and components checked with axe in both color schemes, plus guard tests for unpaired colors and for stale compiled CSS (also shown as a development banner).

- A request timeout or an exhausted database pool answers 503 with `Retry-After`, not 408.
- `offrails-check` fails on a missing `.env.example` variable (`[env]`) and on a bare `n/a` STRIDE row.
- New settings `APP_SHUTDOWN_DRAIN_SECS` and `APP_DEV_HTTP_PORT`; development allows 1000 attempts per rate-limit window.

- **Introspection for agents:** `GET /dev/introspect.json` (development only, absent in production and test, tested) and `app introspect` report routes, redacted config, migrations, jobs, realtime (signal subscribers, connections per member and transport, topics), assets, the browser protocol and CSS staleness. The workflow loop, the Definition of Done, `cli.md` and the app's `AGENTS.md` tell agents to ask it before guessing ([dev-tools](guides/dev-tools.md#introspection)).
- **Fixed: `offrails upgrade --help` launched the upgrade agent** (0.5.0 ignored upgrade's arguments; in 0.6.0, `update --help` still ran the installer and `check --help` ran the checker). Every subcommand now answers `-h`/`--help` (and `offrails help <command>`) with its own help, exits 0 and does nothing else. Unknown commands and flags exit 2 with usage, and `update` validates installer flags before downloading. `new` and `upgrade` never start an agent from a non-interactive shell without `--yes` (or `OFFRAILS_YES=1`): they print the command they would run and exit 3. Exit codes: 0 ok, 1 error, 2 usage, 3 needs `--yes`, 10 upgrade due ([INSTALL](INSTALL.md#the-offrails-command)). `tools/ci/test-install.sh` runs `-h` and `--help` on every subcommand with fake agents on PATH and asserts none starts.
- **`--fw` on an old CLI:** an installed `offrails` older than 0.6.0 silently ignores `--fw` and compares against `~/.offrails/current`. [upgrade](generators/upgrade.md#1-is-there-anything-to-upgrade) now says to run the target release's own script (`sh "$FW/tools/offrails" upgrade --check --fw "$FW"`) or `offrails update` first.
- **Realtime at scale** (measured by a peer: 5,000 SSE watchers on one box, 154 MB, fan-out p50 ≈ 40 ms; the database and rendering were the bottleneck, not streams). Pub/sub keeps one sender **per stream** (`pubsub.subscribe(&stream)`, swept when its last receiver goes), so a signal wakes only that stream's watchers. Hub revocations are keyed per member the same way. Shutdown ends every stream at once (SSE with no `bye`, so browsers reconnect and resume; sockets `bye restart` 1012), then drains for at most `APP_SHUTDOWN_DRAIN_SECS` (5); on 0.6.0 it took 10–35 s with 5,000 streams. The drain is proven here: 2.1 s with a stuck connection and a 2 s bound ([realtime](guides/realtime.md#measured-capacity)).
- **Fixed: the thundering herd on live pages.** Every watcher re-fetched and re-rendered the same fragment after a signal. With 5,000 watchers on one board, one card move cost ~5,000 renders, page loads took 12–25 s and requests timed out. Live regions many people watch now render **once per stream version**. Pub/sub keeps a per-stream version, bumped in `poll_once` where the committed row is observed, before the signal is sent (never at write time). The fragment handler caches the HTML in moka keyed `(stream, version)` with `try_get_with` (single-flight), authorizes every request first, and filtered views bypass the cache. Measured after: GET 10–107 ms, move 10–264 ms, 0 pool-acquire warnings ([realtime](guides/realtime.md#render-once-per-version-the-thundering-herd)).
- **Live re-fetches can't starve user requests, and overload is 503, not 408.** Live regions send `X-Live-Refresh`, and `kernel::live::gate` caps those requests to a third of the pool. The pool's `acquire_timeout` is 5 s, mapped to `AppError::Unavailable`. The request timeout answers 503, and any 503 gets `Retry-After` ([realtime](guides/realtime.md#keep-re-fetches-from-starving-user-requests), [errors](guides/errors-and-logging.md#response-mapping)).
- **Presence over SSE**, for pages that already stream signals and only show a count. Each stream holds a join guard whose `Drop` is the leave; people and tabs are counted; joins and leaves only mark a room dirty; one task publishes one label per dirty room every 250 ms. A connecting tab gets the current label at once. Without coalescing, 5,000 arrivals woke 5,000 receivers 5,000 times. Per process; multi-node needs the pub/sub table ([channels](guides/channels.md#presence-over-sse-no-websocket)).
- **No full reload after a mutation:** move the DOM optimistically, then re-fetch the live region in place with `htmx.ajax` ([frontend-htmx](guides/frontend-htmx.md#no-full-reload-after-a-mutation)).
- **Load testing spec (`tools/loadgen`):** N watchers, M mutations, per-event delivery latency, a presence assertion, and server RSS/fd sampling, with client CPU reported separately. Lessons: pick the target explicitly, cache sessions between runs, about 5,000 TLS+h2 streams per Node process, and never ignore certificate errors on login checks ([realtime](guides/realtime.md#load-testing-toolsloadgen-spec)). Measured capacity is reported as reached, not guaranteed, with the open unknowns: 10–49 of 5,000 connections failed client-side on some restarts.
- **Rate limits never extend a lockout.** The window is fixed from the first counted attempt and refused attempts aren't counted, so retrying while locked out doesn't push the unlock back. **Development allows 1000 per window** (test and production unchanged), decided once in `RateLimiter::new(config.env)` and pinned by a test ([security](guides/security.md#rate-limiting-kernelrate_limitrs)).
- **`n/a` threats in the STRIDE table** are written `| <Category> | n/a: <why> | — | — |`. `offrails-check` accepts that form, counts the rows, and fails a bare `n/a`/`none`/`—` row or a named threat whose test is `—` ([feature-spec](blueprints/feature-spec.md)).
- **Fixed: the Definition of Done's `.env.example` check never found a missing variable** in configs that read through a helper (`parse("PORT", "3000")`); it only grepped `var("…")`. It's now `offrails-check`'s `[env]` rule: every `"SCREAMING_SNAKE"` literal in `src/config.rs` must be in `.env.example`, with fixture tests. In the reference app it sees 27 variables where the old grep saw 23.

## 0.6.0 (2026-10-13)

### What's new

- **Live pages no longer stall past about 6 tabs:** `serve` speaks HTTP/2 over direct TLS, and `bin/dev` serves HTTPS by default.
- **`tools/offrails-check`** (`offrails check`): a script that fails on an inconsistent `AGENTS.md` header, uncited acceptance criteria, feature specs without a STRIDE table, missing tenancy suites and unscoped lookups. It is the first step of the Definition of Done and of CI.
- **Tenancy enforced by the compiler and tests:** with accounts, model lookups take the actor (`find_for`, `all_for`, `destroy_for`), and every app with accounts gets `tenancy_test.rs` and `guard_test.rs`.
- **Fixes from apps that shipped "green":** a user locked out at about 5 tabs (connection cap 8, now 128), pages loading without htmx, a fresh database crashing `serve`, and a logged-out stream redirecting instead of answering 401.
- **`offrails upgrade --check --fw <dir>`** checks or upgrades against any release and exits 10 when an upgrade is due.
- **Rules for weaker models:** a `NEVER` list in the app's `AGENTS.md`, a command for every Definition of Done item, and evidence before any retry, sleep or raised limit.

### Breaking changes

- Direct TLS: new `APP_TLS_CERT`/`APP_TLS_KEY` settings, `bin/dev-cert`, and `bin/dev` serving HTTPS unless `APP_TLS=off`.
- Apps with accounts: raw model `find`/`destroy` become `pub(in crate::models)`, so handlers must move to the scoped functions (the compiler lists every caller), and the two tenancy suites are required.
- `offrails-check` runs first in the Definition of Done and in CI, and fails until the app passes it.
- A logged-out request to `/streams/…` answers 401, not 303 to the login page.

### Upgrading

The numbered **App migration** list (steps 1–14) after the entries, for 0.3.x, 0.4.x and 0.5.0 apps, plus the instant-navigation note at the end. The procedure is in [upgrade](generators/upgrade.md).

### Full list of changes

Hardening from a 0.3.0 Kanban built by another agent that shipped "green" with three P0 defects. The rule this release follows: **mechanical over prose**. Each fix is a command that proves it, a template, a compile error or a failing check.

- **Fixed: live pages stalled past ~6 tabs.** Browsers allow about 6 HTTP/1.1 connections per origin across all tabs, and each live page holds one or two open (signals + socket). The 7th tab's stream, then its page loads, queued forever. Browsers only speak HTTP/2 over TLS, so `serve` now does **direct TLS with HTTP/2** (`axum-server` + rustls, ALPN `h2`, `APP_TLS_CERT`/`APP_TLS_KEY`), `bin/dev` serves **HTTPS by default** (`bin/dev-cert` makes a local certificate with mkcert or openssl; `APP_TLS=off` for http), and `APP_URL`'s scheme follows. Spec: `guides/channels.md` (protocol, transports, security), `guides/realtime.md` (resume). - **Fixed: signals sent while a tab was disconnected were lost** (a deploy, a restart, a blip): live regions silently went stale.
