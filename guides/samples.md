# Samples: optional reference code

> **TL;DR**
> - Samples are tested, security-reviewed code for the parts most apps need: mailer, dev mailbox, jobs, jobs dashboard, auth (core, password, magic link, TOTP), realtime, dev dashboard. They live in a separate repo, **<https://github.com/Rust-Off-Rails/samples>**, tagged per framework release.
> - **Optional, always.** The framework stays Markdown; the guides are the spec. A sample is a head start an agent may *offer*. The human decides; nothing is vendored automatically, and working code is never replaced without their yes.
> - Adopting one: fetch the tag matching `.offrails/VERSION`, read its README (*Adapting it*, *Do not change*) and CHECKS.md, copy and adapt, keep every `// SECURITY:` and `// INVARIANT:` marker and the tests CHECKS.md cites, then run the Definition of Done on both databases.
>
> Read the rest when you offer a sample (interview, upgrade) or adopt one.

The guides say what each part must do. A sample is that part **built**: compiled, tested on SQLite and Postgres, checked by `offrails-check`, `cargo deny` and `cargo audit`, given a threat model, and reviewed adversarially. It follows the framework's conventions exactly, so copied code looks like code you would have written. From the moment it's copied, the app owns it. There's no crate, no update channel and no runtime link back.

## Rules

1. **Offer, don't impose.** Samples come up in two places: the interview's head-start question ([interview](../interview.md#then-confirm-the-plan-once-before-generating)) and the upgrade step that offers them ([upgrade](../generators/upgrade.md#7b-offer-the-samples)). Say what a sample adds over what the app has or would get from the guide, honestly, including what it costs (more code, more tables, its own routes). Then let the human pick: **adopt**, **borrow ideas** (port one feature into the app's own code) or **skip**. Record the answer in `docs/decisions.md`.
2. **Never replace working code without consent.** An app's hand-built mailbox that passes its tests stays until the human says otherwise.
3. **The guide wins.** A sample may do more than its guide (more screens, more checks). Where it contradicts a rule in `.offrails/` (a security non-negotiable, a convention), follow the guide, note the difference in `docs/decisions.md` and tell the human. That's a samples bug worth reporting.
4. **Keep what makes it safe.** `// SECURITY: … (test: <name>)` and `// INVARIANT: … (test: <name>)` markers stay, and so does every test they name and every test in the sample's CHECKS.md table. Change `// APP:` lines freely; that's what they're for. `// WHY:` explains a choice: change it only once you've understood it.
5. **Prove it in this app.** Run the sample's own tests plus the Definition of Done on SQLite **and** Postgres. Add the sample's CHECKS.md STRIDE rows to the feature spec that uses it (`offrails-check` then verifies the tests exist).

## Using one

```sh
V=$(head -n1 .offrails/VERSION)
git clone --depth 1 --branch "v$V" https://github.com/Rust-Off-Rails/samples ../offrails-samples   # outside the app; a tag, never main
```

If that tag doesn't exist, the samples haven't been released for this framework version: say so, and use the newest tag only with the human's OK (its `FRAMEWORK_VERSION` file names the release it was proven against). Then for `<name>`:

1. Read `samples/<name>/README.md` whole (what it adds, *Install*, *Adapting it*, *Do not change*), `CHECKS.md` (the threat model and the test behind each row) and `sample.toml` (crates, dependencies on other samples, wiring).
2. **Check what it builds on.** Every sample is proven in the samples repo's `host/`: an app generated by `new` (htmx) **without** the mailer, dev mailbox, job queue and jobs dashboard (those are samples), and **with** a few kernel pieces the samples use: the theme switch (`kernel/theme.rs`, `kernel/cookie.rs`, `POST /theme`, the `offrails_theme` cookie), `kernel/redact.rs` (token routes in logs, `redact::text`), `Chrome::stylesheet`/`script` in `kernel/ui.rs`, and the anchors. `host/docs/decisions.md` lists each one with its reason. When your app lacks one that the sample's files `use`, port it from `host/` first (`cargo check` names what's missing), and when your app has its own version of a part the sample ships (say, `kernel/mailbox.rs` from `new`), the sample replaces it: remove yours only once the sample's tests are green.
3. Install it. **By hand:** `cargo add` each line of `crates` (never with a version), copy `files/` to the same paths, replace the host crate name `offrails_host` with yours, and apply each `[[wire]]` at the spot its README describes. **Mechanically:** `../offrails-samples/tools/install.sh <name> .` copies files, installs dependencies first, applies the wiring at `// samples: <anchor>` comments, and refuses to overwrite a file that differs (it names each conflict, and each missing anchor, without changing anything). Each sample's `PROMPT.md` is the same procedure as a ready-to-paste prompt.
4. `cargo fmt --all`, `cargo run -- routes`, then the [Definition of Done](../workflow.md#definition-of-done) on both databases.
5. Log it: `YYYY-MM-DD: adopted sample <name> v<version> (<what was adapted>)`. Reconcile the app's `AGENTS.md` notes if the sample's routes or commands differ from the guide's.

A sample that ships a migration ships it with a fixed timestamped name. In an app that already has the equivalent table (from `new` or an earlier sample), **don't copy that migration**: reconcile the table with a new migration, per [upgrade step 4](../generators/upgrade.md#4-reconcile-dont-re-create), and never edit an applied one. The auth samples bring their own schema (`users` with `email_verified_at`, `sessions`, `user_tokens`, `auth_events`, credential tables). In an app that already has accounts, adopting them is a data migration, not a copy: plan it as one and show the plan first.

## Anchors

Shared files (`routes.rs`, `config.rs`, `state.rs`, `main.rs`, `kernel/mod.rs`, `migration/src/lib.rs`, `tests/app/main.rs`, the layout, `.env.example`…) carry one-line comments where a sample inserts code: `// samples: routes`, `{# samples: nav links #}`, `# samples: env`. `install.sh` inserts each wire **above** its anchor, indented like it, so the next sample finds the anchor too. Apps generated from 0.7.0 have them ([new](../generators/new.md#4-rust-skeleton), step 13). Older apps don't, so `install.sh` refuses and names each missing one. Either add the anchors, or apply that wiring by hand (each README's *Wiring* section says where in words).

- **An anchor is a line of its own, never a trailing comment.** `rustfmt` leaves a comment that stands alone on its line where it is: in a `vec![…]`, a `match`, a struct literal, between the links of a builder chain, after a block of `mod` lines. A comment **trailing** code travels with that code instead: `pub mod z; // samples: kernel mods` moves to wherever `rustfmt` sorts `mod z`, and `.route(…) // samples: routes` stays glued to that call when the chain is reflowed. An insertion "above" such an anchor lands in the wrong place, so `install.sh` refuses it. (Checked with rustfmt 1.99, edition 2024, 2026-10-16.)
- A standalone anchor also splits `rustfmt`'s `mod` sorting into groups: a `pub mod x;` inserted above `// samples: kernel mods` is sorted among the lines above it and never crosses the anchor.
- Inside a builder chain or a `vec![…]`, put the anchor where a whole new element or `.layer(…)` line fits; a wire's `text` is always a complete element.
- After `cargo fmt`, every anchor must still stand alone: `grep -rnE '[^[:space:]].*(//|\{#|#) samples: ' src templates migration tests | grep -vE ':[[:space:]]*(//|\{#|#) samples: '` prints nothing.

Each row says what the sample adds over what the guide alone leads you to build. Use it to describe the sample honestly when you offer it.

| Sample | Guide | Depends on | What it adds |
|--------|-------|------------|--------------|
| `mailer` | [mailers](mailers.md) | — | The adapters (SMTP, dev mailbox storage, log, memory), previews, a `send_test_email` task to prove SMTP works, and header-injection checks before anything is sent |

| `jobs` | [jobs](jobs.md) | — | The Oban-style queue, finished: `SKIP LOCKED` claims on Postgres, typed args, backoff with jitter, unique jobs, priorities, scheduled and cron jobs, rate-limited queues, batches, timeouts, orphan rescue, graceful shutdown, pruning, `app jobs`; args and failure messages redacted wherever they're shown or searched |
| `jobs-dashboard` | [jobs-dashboard](jobs-dashboard.md) | jobs | `/admin/jobs` as an operations console: live counters, throughput and queue-wait charts, a now-running lane with progress, queues with pause/resume, worker success rates, **errors grouped by root cause**, job timelines with every attempt, cron with run-now, bulk actions; keyboard and mobile friendly |

| `auth-totp` | [auth](auth.md) | auth-core | Two-factor with an authenticator app: QR enrolment rendered on the server, confirm-before-enable, a code step after any sign-in method, replay protection, 10 hashed recovery codes, "trust this device for 30 days", secrets encrypted at rest |
